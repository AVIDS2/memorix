# Memorix 1.2 Evaluation Harness

The 1.2 evaluation harness prevents product claims from drifting away from
observable retrieval behavior. It evaluates a normalized task Workset using
deterministic requirements, not an LLM judge.

## What It Checks

For each task fixture, every compared Workset is checked for:

1. required start files;
2. required evidence identifiers;
3. required cautions for unsafe or incomplete state;
4. a strict token ceiling.

The same fixture can compare a memory-only answer, the current Project Context
answer, and a future 1.2 candidate Workset. A result only passes when it
contains every required item and stays within budget.

The initial current-context baseline is 320 tokens. The candidate-workset
budget is 180 tokens for the same fixture, so a future implementation must
preserve evidence and safety signals while becoming more compact.

## Fixture Coverage

| Fixture | Boundary being tested |
| --- | --- |
| typescript-auth | TypeScript source and code-bound auth decision |
| python-worker | Python source and retry behavior |
| go-service | Go source and health timeout |
| docs-only | Project knowledge that has no code file |
| dirty-worktree | Uncommitted changes must stay visible |
| deleted-symbol | Removed source evidence must become a caution |
| incomplete-scan | Scan limits must not be formatted as complete truth |

Fixtures live under tests/fixtures/workset-evaluation/. They are intentionally
small repositories rather than copies of the Memorix codebase, so success does
not depend on Memorix-specific naming or history.

## Running It

Run the harness without network access or model credentials:

~~~powershell
npm test -- tests/evaluation/workset-evaluation.test.ts tests/evaluation/current-context-baseline.test.ts tests/evaluation/fixture-corpus.test.ts
~~~

The current-context baseline test runs the existing Auto Context path against
real local fixture repositories. Future phases must add their real Workset
adapter to this harness before claiming retrieval, wiki, workflow, or provider
quality improvements.

## 1.10 Task Matrix

The 1.10 contract adds a deterministic task matrix in
`src/evaluation/context-task-matrix.ts` and
`tests/evaluation/context-task-matrix.test.ts`. It contains 20 cases across
continuity, retrieval, safety, runtime, and integration boundaries. The cases
cover first setup, cross-host recovery, stale and conflicting evidence, CJK and
large-store retrieval, embedding fallback, poisoning and abstention, project
isolation, HTTP session/handle expiry, project switches, and adapter doctor
parity.

Every case records the same metric contract: first-action correctness, recovery
success, memory hit precision/recall, stale and conflict rejection, abstention
precision, input/output tokens, p50/p95 latency, RSS, fallback/degraded counts,
and review cost. The matrix is a testable specification; it does not contain
measured scores. Run its contract gate with:

~~~powershell
npm run gate:context-matrix
~~~

The runtime gate executes the same 20 cases against real Workset, compact
retrieval, CodeGraph freshness, binding-store, and adapter-registry paths. It
also runs the packed 40k large-store transport gate and injects its measured
context latency/RSS into the large-store case:

~~~powershell
npm run gate:context-runtime
~~~

This is intentionally a separate release gate from the ordinary test suite:
it rebuilds the packed runtime and seeds 40,000 records across SDK, HTTP MCP,
stdio hook, and reopen paths. The normal suite still runs the pure runner
contract and skips the capacity-sized fixture.

### Current Retrieval Baseline

The existing deterministic session replay exam provides the first measured
baseline for the 1.10 matrix. With embeddings disabled, four fixed questions
achieved 4/4 hit rate, a maximum turn size of 277 tokens, and zero over-budget
turns. The no-dedup comparison showed 4 duplicate displays out of 16 (25%);
the surfaced-ID dedup path showed 3 out of 16 (18.75%) while retaining 4/4
hits. This is a retrieval/session baseline for the mapped continuity and
retrieval cases, not a score for the remaining matrix cases.

### Retrieval Receipt Contract

Schema version `1` receipts now share these measured fields across compact
engine, MCP `memorix_search`, and CLI `memory search --json`:

- `mode`, `resultCount`, `selectedCount`, and `tokenCount`;
- `candidateCount`, `omittedCount`, and `omittedByTokenBudget`;
- `fallbackUsed` and an optional bounded `fallbackReason`;
- `derivedViews` for FTS, Orama, embedding, and CodeGraph generation,
  freshness, rebuild status, and bounded failure reason;
- request-level `elapsedMs`.

The receipt remains metadata-only: query text, raw memory narratives, and local
paths are not added to it.

### Reproducible 1.9.11 to 1.10 Comparison

The same `scripts/benchmark-retrieval.mjs --records 1000 --runs 20` command was
run from the `v1.9.11` tag and the current 1.10 main line on Windows Node
`v22.22.3`, with embeddings and LLM disabled:

| Version | Seed/index | Specific p95 | Broad p95 |
| --- | ---: | ---: | ---: |
| 1.9.11 | 1,221.509ms | 9.283ms | 12.301ms |
| 1.10 main | 1,245.802ms | 8.925ms | 12.298ms |

The benchmark is a hot in-process SDK lexical measurement, not a cross-platform
SLO. The specific path improved by about 3.9% in this run and the broad path was
effectively unchanged; the result is retained as a baseline rather than a claim
of statistically significant performance improvement.
