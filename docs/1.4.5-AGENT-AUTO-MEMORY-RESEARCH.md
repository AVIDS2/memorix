# Research: Claude Code Auto Memory and What Memorix Should Borrow

> Status: research note (2026-08-14, against the 1.4.5 line). This document
> records findings and direction; it is not a shipped feature and not a claim
> that any item below is implemented.

## Question

Claude Code's Auto Memory gives a single agent a file-based, recallable
workspace memory: `~/.claude/projects/<git-root>/memory/` with a `MEMORY.md`
entrypoint index and typed memory files. What is the design, how does it
compare with Memorix, and which parts are worth absorbing?

## The design, in brief

- Pure Markdown files, no database, no vector store. One directory per
  sanitized Git root, shared across worktrees of that repository.
- `MEMORY.md` is the entrypoint index: at most 200 lines AND 25 KB, one
  `- [Title](file.md) — one-line hook` pointer per line, loaded into every
  session. The knowledge lives in topic files, loaded on demand.
- A closed four-type taxonomy (user / feedback / project / reference), each
  type with explicit `<when_to_save>`, `<how_to_use>`, and `<body_structure>`
  rules. Each memory file carries frontmatter whose `description` field is
  written for the recall system, not for humans.
- The core saving rule: only store information that cannot be derived from
  the current project state. Code, file paths, and Git history are
  re-derivable and do not belong in memory.
- Recall is a lightweight model side-query that picks at most 5 relevant
  memories from the manifest, with denoising for recently used tools and
  dedup of already-surfaced files.
- Memory is injected as a user-context message (prompt-cache friendly).
- Drift defense is prompt-level: a memory that names a file, function, or
  flag is a claim about the past — verify before recommending. An explicit
  "ignore memory" instruction means proceed as if `MEMORY.md` were empty.
- Consolidation ("dream") is time/volume-triggered, merging contradictions
  and pruning stale entries. Long-running sessions may switch to append-only
  daily logs that a later pass distills.
- Security: the memory directory resolves only from user-level input
  (environment override or a user setting). Project-level settings are
  deliberately excluded from that resolution chain, so a hostile repository
  cannot redirect memory storage to arbitrary paths.

## Comparison with Memorix

| Aspect | Claude Code Auto Memory | Memorix (1.4.5) |
| --- | --- | --- |
| Audience | One agent, one product | Any MCP/CLI/SDK/hooks agent, shared |
| Storage | Markdown files | SQLite canonical store + Orama search |
| Entry injection | Full index, fixed 200-line/25 KB cap | Task-lensed Workset, budget-governed |
| Taxonomy | Closed 4 types | 11 observation types + reasoning + Git + long-term |
| Recall | Paid model side-query (needs a key) | Local BM25 primary + bounded semantic fallback |
| Drift defense | Prompt-level verify-before-use | Freshness, attribution guard, evidence governor |
| Cleanup | Time/volume-triggered consolidation | Retention + dedup + consolidation pipeline |
| Path security | User-level-only resolution | User-level-only by construction (env var only) |

The critical review's complaint — memory trapped in one product's sandbox,
no cross-agent sharing — is exactly the space Memorix occupies.

## What Memorix should borrow (directions, not commitments)

Shipped (2026-08-14, continuing on the 1.4.x line):
1. **The "only store the underivable" rule, made explicit.** Now part of every
   generated guidance file, with the dual-channel rule and the verify-before-use
   / ignore semantics.
2. **Dual-channel feedback.** Guidance now tells agents to record validated
   approaches and explicit user confirmations, not only corrections.
3. **Session-level dedup of already-surfaced memory.** `memorix_search`
   demotes rows already shown in the same session (never removes them) and
   remembers the surfaced set per session; measured 25% → 19% duplicate rate
   with hits and budget unchanged.
4. **Explicit ignore semantics.** Guidance now states the contract: an ignore
   instruction means proceed as if memory were empty.
5. **Keep the security boundary tested.** Pinned by
   `tests/config/data-dir-boundary.test.ts`.

Scoring lives in `tests/evaluation/session-replay-evaluation.test.ts`
(retrieval) and `tests/evaluation/guidance-content.test.ts` (guidance); both
are deterministic and offline. A future change to these behaviors must update
the pinned scores only with a measured improvement.
